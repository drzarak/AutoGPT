## 2024-06-06 - SSRF Mitigation Bypass Pattern in Wrapper Library Design
**Vulnerability:** Several integration and webhook handlers (`todoist.py`, `twitter.py`, `github.py`, `slant3d.py`, `fact_checker.py`) bypassed the platform's custom SSRF mitigation by directly importing the standard `requests` library instead of the secure wrapper (`backend.util.request.requests`). This allowed these modules to potentially make outbound HTTP requests to blocked or private IP ranges (e.g., internal metadata endpoints or local services).
**Learning:** This architectural vulnerability arises from the fact that the custom `requests` wrapper only mocks the core HTTP methods (e.g., `.get()`, `.post()`), but it fundamentally fails to expose essential class definitions like `requests.Response` (for type hinting) and exception classes like `requests.exceptions.HTTPError` (for try-except blocks). Consequently, developers are forced to either alias the standard library alongside the secure wrapper (e.g., `import requests as std_requests`) or revert to the standard library entirely to maintain access to these objects, easily leading to accidental circumvention of the security wrapper when executing requests.
**Prevention:**
1. The custom wrapper module (`backend.util.request.py`) must be refactored to explicitly export necessary classes from the standard library (e.g., `Response`, `exceptions`).
2. Establish a linting rule to proactively prohibit direct `import requests` in backend application code, enforcing usage of `backend.util.request`.
